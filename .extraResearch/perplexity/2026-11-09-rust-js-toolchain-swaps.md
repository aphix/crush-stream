> Question: Which tools written in Rust (or other compiled languages) replace parts of a JavaScript and TypeScript development toolchain, such as linting, type checking, transforming, bundling, testing and coverage, and how close is each to a drop-in replacement for the tool it replaces? What speedups are measured? Cite the projects.

Several compiled-language projects can replace **parts** of the JavaScript/TypeScript toolchain, but none is a universally drop-in replacement for the entire ecosystem. Compatibility ranges from highly practical for formatting/transformation to incomplete for type checking, bundling, testing, and coverage.

| Area | Compiled-language tool | Replaces | Drop-in closeness | Reported speed |
|---|---|---|---|---|
| Linting and formatting | **Biome** (Rust) | ESLint + Prettier | **High for common JS/TS linting and formatting**, but not all ESLint plugins, processors, or type-aware rules | Project-specific benchmarks vary; broad claims such as “50–100× faster” generally refer to Oxlint or selected workloads, not universal Biome performance[9] |
| Linting | **Oxlint** (Rust) | ESLint | **Medium to high** for supported rules; lower where projects depend on custom ESLint plugins or type-aware behavior | Oxlint is reported as **50–100× faster than ESLint** on comparable rule sets in secondary reporting; this should not be treated as a universal result[9] |
| Linting with type information | **tsgolint** / related Oxc work | ESLint type-aware rules | **Experimental to medium**; rule and configuration compatibility is incomplete | No reliable primary-project benchmark was returned in the available results |
| Type checking | **ts-r** (Rust) | `tsc` / TypeScript compiler | **Low to medium today**: it aims for matching diagnostics, but compiler behavior and edge-case compatibility are not yet equivalent | Its project reports **2.0–5.4× faster** checks on tRPC, date-fns, and RxJS; examples include 2.1× on tRPC, 2.0× on date-fns, and 5.4× on RxJS[2] |
| Type checking | **ts-r** | `tsc` | Not yet drop-in: its README reports exact output on **97.7% of TypeScript conformance tests**, implying remaining incompatibilities[2] | It reports **1.9× faster startup**, **1.5× faster** on a sample build, and the checking gains above[2] |
| Type checking | **Bun’s `bun check`** (Zig/C++) | `tsc` for many workflows | **Medium** as a command-line checker, but not a complete replacement for TypeScript’s language service, compiler APIs, or every `tsc` option | A third-party comparison reports VS Code checked in **1.75 seconds versus 12.58 seconds** for TypeScript 7 on a 64-thread Linux machine; this is benchmark-specific[6] |
| Type checking | **tsz** (Rust) | TypeScript checker | **Early/low**: performance-oriented and still developing, rather than a mature `tsc` replacement | Its project states a goal of being **2× faster than `tsgo`** and reports **3× faster** results on small-file samples[5] |
| Transpilation | **SWC** (Rust) | Babel and parts of TypeScript transpilation | **High for syntax transformation**, especially common Babel presets; not a type checker and not identical to every Babel plugin | The available results did not provide a project-primary benchmark with a single generally applicable speedup |
| Transpilation/parsing | **Oxc** (Rust) | Babel/parser-related tooling and parts of the JS transform pipeline | **Medium** and rapidly expanding; APIs, plugins, and semantics differ from Babel | No dependable primary benchmark was available in the returned results |
| Bundling | **esbuild** (Go) | Webpack, Rollup, parts of Vite’s bundling pipeline | **High for standard application bundling**, but Webpack loaders/plugins and unusual Rollup behavior may require migration | In the `ts-r` project’s sample benchmark, esbuild completed a build in **1.41 s**, versus **963 ms** for `ts-r-build`—about **1.5× faster** for that workload[2] |
| Bundling | **Rolldown** (Rust) | Rollup, and the bundling layer used by Vite | **Medium to high** for Rollup-style projects; ecosystem/plugin compatibility is still the key limitation | A secondary report claims **10–30× faster than Rollup**, but the available result does not establish a broadly reproducible benchmark or primary-source methodology[10] |
| Bundling and integrated dev tooling | **ts-r** (Rust) | Parts of `tsc`, esbuild, runtime/dev-server workflows | **Low to medium** as a full replacement; it is explicitly designed as an integrated tool rather than a set of established-compatible drop-ins | Its README reports **1.5× faster** than esbuild on one build benchmark and **1.9× faster** startup than esbuild[2] |
| Testing | **Vitest** (TypeScript/JavaScript, powered by Vite) | Jest | **High** for many Jest test suites, but not compiled-language-based and not fully compatible with every Jest mock, environment, or plugin | No relevant measured speedup was returned in the available results |
| Testing | **Bun test** (Zig/C++) | Jest, Mocha, parts of Node test workflows | **Medium**: Jest-like APIs are available, but mocks, environments, reporters, and Node compatibility can differ | The available results mention type-check-before-test behavior but do not provide a comparable, project-primary test-speed benchmark[6] |
| Coverage | **c8** (Node/V8) | Istanbul/`nyc` | **High** for V8-based Node coverage, though it is not a Rust replacement | No speed result was returned |
| Coverage | **Bun coverage** (Zig/C++) | `nyc`/c8-style coverage in Bun workflows | **Low to medium** outside Bun; runtime and instrumentation differences can affect reports | No reliable comparative coverage-speed measurement was returned |
| Coverage | **cargo-llvm-cov** (Rust) | Rust coverage tools, not JS/TS coverage | **Not a JavaScript/TypeScript replacement**; relevant only when the tested code is Rust | No JS/TS replacement claim applies |

## Practical assessment

- **Closest drop-in replacements:** Biome for formatting and mainstream linting; SWC for common transpilation; esbuild for conventional bundling.
- **Strong replacements with migration work:** Oxlint for ESLint-heavy projects, Rolldown for Rollup/Vite-style builds, Bun test for projects willing to adopt Bun’s runtime semantics.
- **Fast but not yet drop-in type checkers:** ts-r, Bun’s checker, and tsz. Type checking has the hardest compatibility problem because matching TypeScript’s diagnostics, module resolution, declaration handling, language-service behavior, and compiler APIs is much more demanding than parsing or transforming code.
- **Testing and coverage remain fragmented:** compiled runtimes can execute tests quickly, but Jest/Mocha compatibility and coverage-report equivalence are not yet as standardized as linting or bundling.
- **Treat speedup figures cautiously:** the strongest numbers available are project- or workload-specific. For example, ts-r provides concrete benchmark tables—up to **5.4× faster** type checking and **1.5× faster** sample building[2]—whereas “10–30×” bundling and “50–100×” linting claims come from secondary reporting and should not be generalized[9][10].
