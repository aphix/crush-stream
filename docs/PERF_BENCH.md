# Perf bench

How to time the game, and what each number means. The budget is a 240 Hz frame (**4.2 ms**); a frame over 16.7 ms is a
dropped 60 Hz frame. Perf numbers need a quiet box: record `/proc/loadavg` and the GPU clock (`nvidia-smi`) with every run,
and compare builds inside one session with alternating runs.

## Benches

| Bench | Run | Measures |
|---|---|---|
| JS kernels | `npm run bench` (`scripts/bench/kernels.mjs`; `scripts/bench-physics.mjs` stays as its old entry) | wall ms of the plain-JS kernels over a fixed loop; "static" rows repeat one input, "animated" rows step a moving deformation |
| Browser frame | `node scripts/bench-browser.mjs [--url …] [--cars 2,10,16,24,32] [--modes fleet,derby,race-oval,race-rally,race-city] [--seconds 8] [--warmup 2] [--out bench.json] [--vsync]` | wraps `tickInner`, `fixedStep`, `updateSkin` and `renderer.render` on the live `window.__crush` and reports their times and the frame interval |
| Program links | `npm run check:programs -- --url <server>` (`scripts/check-programs.mjs`) | fails if any GPU program links after the boot warm-up or during a race (about 3 min; needs a server and a browser) |
| In-app card | open `/crush/?bench=city` or `/crush/?bench=strip` | the real game on the real clock on any device, phones included (below) |
| Scenario bench | `flock -x <lock> node scripts/bench/bench.mjs run <scenario>... [--arm name:knob=v,...]...` (`npm run bench:scenarios`; `list` names the scenarios) | the sim alone (no engine, no render, no AI) on named fixed scenarios, one variable apart, each arm its own process in ABBA order behind a load gate (below) |

### The scenario bench: `scripts/bench/`

Every A/B of a sim cost cut runs here, so a number quoted later compares like for like. `scenarios.ts` builds each scenario on the Fleet pad's flat ground over a bare `World` (`sim.ts`: the engine's slice, the scripted pedal of each car, `stepWorld`, `settleStep`; the pacer pinned to the 1/240 s slice, one step a frame as `benchRaceEngine` runs the city), with no AI, so drive and plan cost the same in both arms of a row. `scenario-info.ts` says what each row is (the cars, what is held, the **one variable** against its neighbour, the cut it sizes); `bench.mjs list` prints them. The rows: **intact-alone** (16 sedans 40 m apart: the per-car baseline, and the control: with no wreck `epi.on` must change nothing, the digests are equal), **intact-convoy** (the same 16 in two columns inside the lone reach, 5 m nose to tail: the one variable is nearness, sizing the tops reads and pair tests), **intact-convoy-mixed** (the four classes), **wreck-driving-apart**, **wreck-stopped-apart**, **wreck-dead-apart** (8 wrecks of one staged crash, moved 40 m apart keeping their damage: driving, then standing with the drivetrain alive, then dead), **wreck-dead-piled** (the same dead wrecks in a pile: resting-pair work and the freeze/thaw thrash). A wreck row stages ONE crash in an isolated zone with every knob off, then moves each wreck to its place, so both arms start from the same bytes, and applies the arm's knobs afterwards. City, derby and the other maps stay the end-to-end confirmation (the in-app card, `tests`), not the place to look for a cut.

An arm is `name:knob=value,...` over any `epi.*` knob (default arms `off` and `on:epi.on=1`); `--order abba|baab|both` runs the arms there and back, back and there, or both; each run is its own process. The driver reads the load before each run and stops (exit 2) above `--max-load` (default 2, the repo's timing rule) unless `--force`, which runs on and flags the row `LOAD`; take the lock outside (`flock -x <lock file> node scripts/bench/bench.mjs run ...`). `--seed n` gives the engine rows' field (`city`, `city-race`, `dam-spine-race`, `national-mall-race`, `havana-race`) another dice: those races are chaotic, so one seed is one sample of a build's wrecks (a 0.01 m change of the lone reach moved the city race's freezes a second from 402 to 1115 on an unchanged tree): judge a cut on several seeds, per state (`--record`) and per unit, not on one race's wall or churn. The table prints per arm the mean of its runs: ms per sim-second by phase, **us per car-slice** (live + wreck + asleep) by phase (the number to quote: arms that do different work compare per unit), the work counters (`slices`, `pairTests`, `frozenCarSlices`, ...: whether it is an apart or a near row, and whether the lone schedule ran), the frozen share and thaws, the frozen-state breaches, and the end state's digest with the largest pose difference between the arms' first runs (equal digests: the arms did the same work, so whole-sim ms is a valid A/B; otherwise per unit only). `--thaw-sites` counts which call thawed how often (a stack sample per thaw: a run for counts, never for ms). Raw runs go to `.bench/scenarios/<stamp>/` (git ignores it). `scripts/bench/bench.test.ts` holds the driver's rules and runs the control row; `src/game/contact/whole-digest.test.ts` pins the `whole` solver's digest after four staged crashes.

**The epicenter arms watch the frozen wrecks.** An arm with `epi.on` runs with `epi.frozenCheck` on unless its own knobs set it (`epi.frozenCheck=0` for a timing arm): the table's `frozen-state breaches` is then a count, never the 0 of a check that was off. Every 0.5 sim-s the run also reads each frozen wreck's hubs against their car-frame rest places (`hubsOff`): the table prints the worst distance (a hub stands a face's shove, up to 0.35 m, off it; the drawn wheel sits at its hub's frame x and z) and a `FLAG` line when a check found one over 0.5 m. Before the hub pin at the freeze (`HUB_PIN_MAX`, `integrateWreck`) a derby wreck that froze mid-spin kept a hub 0.7-3 m off its place (24 cars in 17 of 40 matches), and a bench with the check off showed 0 breaches.

**The ground queries (`--ground`, `--prof`, `--verify`, pseudo-knob `bake=0`).** `--ground` turns on the counters and a coarse section clock of `surfaces.ts`'s queries (`world/ground-clock.ts`: calls per car-slice for every query and per-point outcomes, us per car-slice and share for the point queries, the wheel's contact, the edge/ridge crossings and the ground's own reads; the cheap gates `staticTop`/`solidTop`/`topsTop` are counted, not timed, since a clock read costs 230 ns; the clock inflates the phases, read shares only); off, every query pays one branch. `--prof` runs the V8 sampler over the measured window only and prints inclusive and self ms per sim-second with each function's heaviest lines. `--verify` answers every point query and wheel contact twice, baked and by the layered path (`BAKE.on` false), and compares the bits (the far answer: `C_H`, `C_OWNER`, `C_ARG` and its travel proof): the table prints the counts and `MISMATCHES`, which must be 0. `bake=0` in an arm switches the bake off (`PLAIN_LISTED` cells, the far answer): the two arms must have equal digests; `ground-bake.test.ts` holds both to the layered path on a sloped grid with a tying prism, and its far-answer row goes red with the cell's normal bound dropped.
**The terrain bound off the baked grid (`bake=0` / `bake=1`, `--verify`).** A car off a course's baked grid stands on the base terrain's gaussian hills, whose bound over a point's box (`staticTop`, the gate of `readPoints`) was every hill's whole height: the Mall's one hill held every point of a car kilometres from it up 2 m, so ~46 of ~130 cage points per slice went on to a full point query for nothing. The bound is now each hill's height at the box's nearest point to its centre (`surfaces.ts` `hillsTop`), 1e-12 past a precomputed cutoff (`hillFar`); `bake=0` keeps the old sum. `--verify` asks every cage point only the new bound cleared the old way too (`hill bound check`: contact rows and `nearing` must be 0) and prints the least of (bound over a point's box less the terrain's height at the point), which must be >= 0. `terrain-bound.test.ts` holds the bound over a sampled lattice and goes red measuring from the box's centre instead.
**What diverges, how much, when (`--trace <dt>`):** each car's pose and every mass's world position every `dt` sim seconds from the start of the warm-up; the table prints, for every arm against the first, the worst car's body distance, body turn and worst hull point at about twelve checkpoints (with the car), the first time each passes a visible guide (2 cm, 1 degree: a judgement printed beside the numbers, not a measured limit) and the worst of the run. **Read it against the sim's own sensitivity:** the pseudo-knob `nudge=<m>` (an arm: `--arm n1um:nudge=1e-6`) moves every mass of car 2 that far in x with every knob off, so a whole-against-whole arm shows what the sim does to a micrometre. On `wreck-pile-pushed` (8 dead wrecks thrown together 1.4 m deep, pushed apart in every slice) 1 micrometre gives an 11.5 cm worst body divergence and 10 micrometres 13.1 cm: chaos (discrete pushes of 1 m/s x the slice flip on a micrometre), not amplification, and epicenter on against off there (19-22 cm) sits inside 2.5 times that; the deterministic staged hits (`epicenter-equivalence.test.ts`) move at most 1 mm for 1 micrometre, which is why their 1.2 cm bar means something. **The freeze's invariant** (`DeformFreeze.settleFreeze`): after the whole-path integrate that caches the frozen centre no `clampLocal` may run until a thaw (a planted hub's clamp pins `local` away from where it stands, and the frozen placement reads `local`: hubRL 15 cm off whole when a variant broke it); `epi.frozenCheck` counts a `followGroup` on a cached frozen car as a breach.

**On WSL** always pass `--vsync` to `bench-browser.mjs`: its default launch is uncapped, and uncapped frame-rate flags drive
the GPU through WSL's d3d12 driver and have crashed the VM. For CPU frame cost, drive the page with
`__crush.advance(seconds, { frameDt, render: true })` at a synthetic `frameDt` (1/240 s for the fleet and derby, 1/80 s in
races): the numbers are then the **CPU cost of the frame the engine does per rendered frame** (sim, camera, FX, render
submit), reproducible and independent of the compositor's pacing; GPU time is not in them.

## The in-app card

`?bench=city` sets up the city, 15 AI racers plus the player's car (the follow camera, the AI drives it), traffic and up
to 6 police, seed 1, aggression 1. The engine's own rAF loop is stopped and each rAF feeds `advance(measured wall dt,
render: true)`, so the pacer's real 8 ms deadline applies. This is the **extended** bench (`&extended=1`): it waits out the grid and 20 s of race clock, measures 30 s of
the game as it runs (after a warm-up sweep of every setting, below), then runs four A/B stretches (pacer, detail, FX tier, sky) on the same race and ends on the replay of its own crash (below). The default bench is the quick one, next. The race plays on under the card afterwards.

`?bench=strip` runs the same card on a controlled course (`world/bench-strip.ts`): a straight race lane up +z, a U-turn of
radius 130 m and a return leg, so the rules see an ordinary one-lap course. Static props stand in a row on the lane's left
outside the wall, an NPC traffic road on its right. The race is the bench's own (aggression 0.5, no police); the page
writes neither the address bar nor storage.

| Parameter | Values | Default |
|---|---|---|
| `props` | `building:20,tree:40,rock:20` (any prefab id, at most 400 each), or `off` | `building:20,tree:40,rock:20` |
| `traffic` | `2x12` (lanes 1 or 2, cars 1–16), or `off` | `2x12` |
| `cars` | racers 2–16, the player's car included | `16` |
| `same` | `sedan`, `hatchback`, `wagon`, `coupe`, `pickup`: every car wears that body; `off`: the fleet's mix | `sedan` |
| `len` | the straight in metres, 1500–12000 | `6000` |

A value that does not parse falls back to its default. Splits: `?bench=strip` (baseline), `&props=off`, `&traffic=off`,
`&props=off&traffic=off` (the bare lane). Any bench (`city`, `strip`, `lab`) also takes `&ultra=1`: the card fetches the Ultra look before its first block and adds an `ultra` arm to the FX A/B (below), or fails if it does not load.

### The quick bench (the default) and the extended bench

A game's built-in benchmark takes 2-4 minutes; the loop took 42-49. The default bench is now the quick one: the four maps (strip, city, biggest course, the National Mall) once each, **one epicenter arm per run** (the entry alternates it from run to run: `crush-bench-next-arm` in the browser's storage, so a run is off and the next on; the card says which, `fetch --ab` pairs a map's off card with the next run's on card of the same device and build), the measured window alone. The extended bench (`startBenchLoop(true)`, `&extended=1`) is what the loop was: every map under both arms, the sweep, the pacer, detail, FX and sky A/Bs and the replay on every page, an opt-in. The entry offers both, each with its planned length (`quickPlanS`, `extendedPlanS`, `bench-plan-time.ts`, from the same constants the bench runs on: `about 3 min` and `about 41 min` with Ultra in the build).

**Before** (the owner's two loops of 2026-10-18, build c83d90c9; seconds a page by stretch, from each card's per-second page series, `.bench/durations.mjs`):

| | warm-up | window | pacer A/B | detail A/B | FX A/B | sky A/B | replay | sweep | page | 8 pages |
|---|---|---|---|---|---|---|---|---|---|---|
| desktop (loop 0ighlloz, 11 pages) | 28 | 40 | 34 | 51 | 70 | 17 | 58 | 14 | 313 | 41.8 min |
| phone (loop ex79afcb, 4 pages) | 41 | 40 | 42 | 63 | 83 | 20 | 61 | 18 | 367 | 48.9 min |

The window was 13 % of a page; 55 % was the four A/B stretches. (Each page's first sweep was 39-41 s, the others 10-12.) **After**, one run of the quick bench on this box (headless Chromium on a software GL at 10 fps, the slow case: its sweep stops run to their frame minimums), the whole cycle, load to the fourth card: **196 s (3.3 min)**; the pages 64 s (the strip: the one sweep, 27 s of it), 42, 44 and 45 s. The plan for a desktop GPU is 157 s with the sweep at 12.5 s (3 tiers x 2.5 s, the epicenter pair, `QUICK`) and each page 3 s of load, 5 s of grid and the 25 s window, with the 4 s card pause between pages. Extended: planned 40.7 min a cycle with Ultra (36.6 without) against the 42.4 measured (the window 40 to 30 s and the A/B block 8 to 5 s, which the earlier change had made 8; the 75 m rung, the pacer's third round and the sky's second stay cut): not longer, as the owner asked, and not much shorter: the extended bench is the opt-in for the A/Bs, the quick one is the answer to the length. A row holds the plan under the measured 42.4 min (`bench-plan-time.test.ts`).

**What the quick page does** (`runBench` with `plan.extended` false): enter the scene, pin the sky, run the grid to green (no race-clock warm-up), **stage a head-on crash at the start line** (`RaceField.crashAtStart`, the first two grid cars 12 m apart at 25 m/s, the replay's own), then record the `QUICK.windowS` = 25 s window with every frame. The staged pair makes the window the same event on every device and in both arms: two starts of the city give the same bit-for-bit window over 6 sim seconds (`bench-scene.test.ts`), where the loop's chaotic AI races differed by up to 14 % between a 25 s and a 40 s mean (the owner's cards: strip:epi 41 fps over its first 15 s and 92 over its 40). The loop's **first page only** runs one sweep (the FX tiers and the epicenter pair, each held `QUICK.sweepStopS` = 2.5 s, 45 frames at least): JIT, programs and heap stay warm across the pages of one page-load, so the later pages have none. A quick card has no A/B arms (`abPace`, `abFx`, `abDetail`, `abSky` are null), no replay and no switch rows; `run: { extended, staged }` says what ran.

**The warm-up ends in the window's state** (the owner's bug: the sweep turned the epicenter on, swept, then turned it off, and the window opened with it on again). Both arms' paths are swept, the stop order puts the window's arm last (`bench-sweep.ts`: off then on for the epicenter page, on then off for the other), in both benches; the knob is on the card each second (`pageSeconds.epi`) and `fetch --ab` flags a window whose first second reads other than the last warm second.

**Every frame, recorded, summarised on the device** (`bench-frames.ts`, `result.frameStats`). The stats.js way: each frame's wall interval, cpu, sim and draw ms, steps, wrecks, ragdoll posts, the sim's 14 work counters and its 10 phases' ms are written into one `Float32Array` sized once (the row of a frame is 31 values; no allocation in a frame: 5 million pushes trigger no garbage collection, `bench-frames.test.ts`), and only the summary leaves the page: the percentiles (median, p95, p99, p99.9, max), the **1 % and 0.1 % lows** (the mean fps of the slowest 1 % and 0.1 % of the frames), the window in **200 ms buckets** (each bucket's frames, mean and max interval, mean cpu/sim/draw, every counter and phase summed over it, the wreck count's largest), and the **spike list**: every frame over 3x the window's median (and 25 ms) is a spike; the worst 64 are listed in time order with their interval, engine ms and the sim's activity in them, and the card counts them all. For the activity columns (wrecks, ragdoll posts, wreck / asleep / frozen car-slices, pair and part contacts, freezes, thaws, steps) it gives the mean in the spike frames against the mean elsewhere, the correlation of the frame interval with it over all frames, and which phase was the largest in how many spikes: `drops coincide with N simultaneous ...` is a number, not a reading. The card prints the lows and one spike line; `fetch-submissions --frames` prints every listed spike with its largest phase and the 200 ms table (`--phases` the stats and the summary line).

**The card on the wire** is columnar: the series and the spike list are `{ cols, dp, n, data }` (the names once, the decimals, one plain number array a column), and the lists of records a card carried (`switches`, `pageEvents`, the hitch rows) are `{ keys, rows }` tables (`wireCard`, `tabulate`: no key repeated per record; `fetch` reads the old lists too). **Sizes**, measured from the four posted cards of the run above: 25.1, 28.6, 27.9 and 28.0 kB raw, **7.9, 9.1, 8.7 and 9.0 kB gzipped** (the series is 125 buckets of 25 s whatever the frame rate, so a desktop card is no bigger). `MAX_JSON_BYTES.bench` is 8 MB, a junk guard: the wire limit is the 3 MB gzipped cap and the proxy's 4 MB body.

### The Lab: `/crush/?bench=lab`

The same card and run in the Lab (`engine-bench-plan.ts` `LAB_BENCH`): no race, a fixed throw sequence instead, with time held at 1x (the slow-mo would stretch each hit over a different share of each block). Every 4 s of sim the next set loads (the HUD's set picker, or Reset for the set already up) and, 0.5 s later, its thrower is let go at a stored launch velocity (`flickLab`, the player's flick): at the house of cards' top car, then at the wall of props, about 30 m/s each, in turn through the window. Each A/B block starts the sequence over, every arm of a round on the same throw (round 1 the cards, round 2 the wall), so the arms see the same hit. The sequence runs on the sim seconds the pacer stepped, so every device steps the same throws per sim-second. The card's second line names the throws and how many the window saw. Every bench's sim speed and ms per sim-second now read the sim seconds the pacer stepped, which is the race clock while a race runs.

### The replay: the run's own crash, played back

Every race bench (`strip`, `city`, `dam-spine`, `national-mall`; not the Lab) ends on the highlight reel, so a card carries replay-playback perf data. After the A/Bs the race starts over (`retry`, seed 1; its recorder with it) and, once it is green, the first two cars of the grid are put head-on on the start line (`RaceField.crashAtStart`: 12 m apart, 25 m/s each, closing 180 km/h; a driver is thrown, the same on every device). The recorder files the crash as a highlight (waits at most 20 s). That clip is recorded by this run on this build and replay version, never a fixture, and is played back through the results reel's own path (`packReel`/`unpackReel`, `ReelDirector.play`: overhead flight, then the crash cam, slow-mo and the thrown drivers) at each FX tier in turn (`minimal`, `low`, `high`, and `ultra` when the page loaded it with `&ultra=1`, set by `setFxTier`): a restart per tier, 0.5 s unscored (the replay's world is built on its first frames), then 12 s scored (`engine-bench-replay.ts`). Each tier reports fps, 1 % low, frame, cpu, sim, draw and GPU ms, and the ragdoll world's step cost. `sim` is the reel's own clip steps (`ReelDirector.takeStepMs`; the engine's pacer does not run while a reel plays). If a run produced no clip (no grid of two cars, the race did not go green in 20 s, the crash was not filed in 20 s, an error) the result has `replay: null` and `replayWhy` says why, and the loop goes on. The page's phase log (`pageEvents`) has a `replay` phase.

The ultra arm is each step's own: the loop runs the same eight steps with `&ultra=1` on each when Ultra is on (`loopultra`/`cycleultra`, [`DEPLOY.md`](DEPLOY.md)), not a second `+ultra` pass of every map. A cycle is strip, city, dam-spine, then the National Mall, **each map twice, the epicenter activation off and then on** (`strip`, `strip:epi`, `city`, `city:epi`, …: the `epi` step's page carries `&epi=1`, which `runBench` turns into `epi.on` = 1 once the race is up and before the warm-up; a share `#` never reaches a bench page, so the Debug link cannot do it; the card says `epicenter ON`/`off` and has `settings.epicenter`; same seed and car count, so a pair differs in the activation alone, and `node scripts/fetch-submissions.mjs <url> --kind bench --ab` prints each pair side by side) (`?bench=city&course=national-mall`: 2753 props, about 500k triangles a frame, the loop's heaviest draw): each step is about 4 minutes on a quiet device, all in the one page (below) (20 s of race clock, the 40 s window, 32 s + 48 s + 48 s (+ 16 s with Ultra) + 16 s of A/Bs after their settle watches, the replay at each FX tier, the warm-up sweep first), so a cycle is about 40 minutes. Card size (the whole POST body's JSON): 8.7 kB (2.9 kB gzipped) for a strip run with the replay at four tiers, from a phone (a card from before the shortening: 18.4 kB, 6.7 kB gzipped); the cap is 48 kB of decoded JSON.

### The loop in one page: what a step starts from, the wake lock, the per-second page state

`driveLoop` (`bench-loop.ts`) runs every step of the cycle (each map, both arms) in the page the Benchmark entry opened: a page load drops fullscreen and releases a wake lock, and on a phone the screen timing out in the middle of a cycle (it did, at the National Mall) throttles the page. `WakeHold` (`bench-wake.ts`) asks for `navigator.wakeLock.request("screen")` before the first step, asks again whenever the page is shown (the browser drops the lock with a hidden page) and releases it when the loop ends; a browser without the API or one that refuses it holds nothing, logs the refusal, and the card says so. A reload onto a newer build (`auto=1`) is the loop's one navigation.

A step starts from what a fresh page has (`enterBenchScene`, `CrashEngine.resetAdaptiveQuality`): the last step's scene left, every Debug knob at its default (the epicenter arm's `epi.on` included), the FX tier on its first tier with a new tier policy (`AutoFx`'s learned ceiling) and a new detail governor (its rung and hold), and the pacer with nothing owed or learned (`SimPacer.reset`: a step that began on the last one's overdrawn frame took its steps a frame off). `bench-scene.test.ts` runs city, city with the activation, the strip, then the city again in one engine, 14 sim seconds each (the grid, the start, the first crash and the pile-up): the city's second visit matches its first bit for bit (the digest of every car's pose and velocity and the pacer's steps). Without the pacer reset the revisit ran its steps one frame off from the sixth frame on (a 1e-17 m/s difference in a car's vertical speed) and its digests diverged by the second second; the cars need no rebuilding (a respawn resets them: the digests match with the same cars). **Not the same as a fresh page:** the JIT and the heap carry from step to step (the point: the settle rule and the warm-up exist for the first seconds); the rival bitmaps stay at the finest size an earlier step reached (they never shrink, above); the ragdoll worker and its Rapier world, the skin kernel's tables and the shader programs persist; the first step of a page is colder than the rest.

`result.pageSeconds` is the page's state each second of the step from its first frame, three strings of one hex digit a second: `flags` (shown 1, focused 2, fullscreen 4, the wake lock held 8; `f` is all four) `phases` (the stretch's `PAGE_PHASES` index) and `sky` (the sky as drawn, below). It is written from the page's events, the hold's flag and the dome's state (`watchPage().tick`: the page's state is not read per frame, the dome's is one getter), a second the hidden page drew no frame in included. `fetch-submissions --ab` reads these seconds as below (what spoils a window is a FLAG, what only happened is a note), with the count of the window's seconds.

### The sky is pinned, never auto

Under `auto` the sky follows the FX tier (`skyDetailFor(mode, tier)`: none on minimal, the 2048 strip on low, the 4096 strip on high and ultra), and the tier is moved by the engine's own policy (`AutoFx`) and by every FX A/B arm, so an auto sky changes what a window or an arm draws while it is measured: the sky's cost would move with the arm under test. The sky depends on nothing else the bench changes (checked by references: `SkyDome.setDetail` is called only by the stage's `syncSky`, from the Sky setting, the FX tier and the time of day, which only a course change moves; the detail governor, the device class and the PMREM studio environment never touch it). So **the bench pins the Sky setting explicitly** (`skyPinOf`): `full` on a race, `off` on the Lab, in force from the end of the warm-up sweep (which visits `off` then `full`, so the strip is loaded and stays in) through the window, every A/B arm and the replay. `full` and `off` draw the same on every tier, so no Auto decision can change them (`bench-sky-pin.test.ts`: with `auto` the drawn sky differs between tiers, the control; pinned, every tier and the Auto policy running for 1200 frames leave it the strip; the Lab's pin draws nothing on every tier). `pinSky` puts a pin in force and waits, at most `BENCH.skyWaitS`, for the dome to draw it: the window never opens on a strip still decoding. The sky A/B sets it both ways, explicitly. Your own setting is put back when the run ends (`settings.skyPlayer`).

**Recorded.** `result.pageSeconds.sky` is the sky as drawn each second (`SKY_DRAWN`, one digit: 0 none, 1 gradient, 2 half, 3 full, 4 loading; `SkyDome.drawn`, read once a frame, written once a second into an array sized once), next to the flags and the stretch of the same second. The card's settings line says `sky full pinned by the bench (your setting auto, put back after; full on every tier), drawn full 40 of 40 window s`, and `fetch-submissions --ab` flags a window with seconds that did not draw the pinned sky (`sky not as pinned N of M s`). The sky arms' settle time and spread are their `switches` rows and `simSpreadPct`, as for every arm.

**Which arm is running.** The card's top left, on a phone too, starts with a label that says `EPICENTER ON` (amber) or `epicenter off` (grey) (`ArmBadge`, `bench-badge.ts`). It reads the knob itself, once a frame (one read and a compare; the page is written only when the arm changes), so it changes in the frame after the in-page loop's step switches the knob (`enterBenchScene`) and while the warm-up sweep turns the activation on and off. The card's header line says `epicenter ON`/`off` and `settings.epicenter` is now read from the knob, not from the HUD's copy of it (`bench-badge.test.ts`, a row in `bench-frame.test.ts` that turns the knob between two frames, a row in `bench-scene.test.ts` that enters the loop's steps in turn).

### The warm-up sweep, the lengths, and the stability check (the extended bench)

**Sweep** (`bench-sweep.ts`). A step first visits every setting the window and the A/Bs will switch, unscored, so the code each runs is compiled and optimised and each one's first draw on this scene (programs linked, targets allocated) is behind it when they are measured: every FX tier (`ultra` when the page loaded it), then, on **a page's first step only** (the JIT, the programs and the heap stay warm across the steps of one page), both pacer pins, every detail rung (no cuts, 50 m, 30 m) and the Sky setting `off` then `full` (waited for, up to `BENCH.skyWaitS`: the strip is loaded and stays in), and on a race the epicenter activation on and off (its freeze and thaw paths run on both arms' pages alike: neither starts colder). A later step's sweep is the FX tiers and the epicenter only, for `BENCH.sweepShortS` each. A setting stays in force for `BENCH.sweepS` wall seconds and at least `BENCH.sweepMinFrames` frames, never past `BENCH.sweepCapS` (a phone at 10 fps needs the frames, not the seconds; the clock is the frames' own intervals, so a hang counts as long as it took). The sweep's frames are the hitch log's `sweep` stretch (`PAGE_PHASES` 7), every one a setting switch, and **its hitches are their own table** (`result.sweepHitches`, and `warm-up sweep: N hitched of M frames` on the hitches line), not in `result.hitches`. After it (`endSweep`) the pacer is unpinned, the bench's Sky pin is in force, the adaptive quality is as the page booted, the scene is entered afresh (`enterBenchScene`), and the step's own warm-up (the grid and `warmS` of race clock) runs: **the sweep leaves the sim untouched** (`bench-scene.test.ts`: the city after a full sweep, run with the window's recording on, is bit for bit the city of the page's first visit, which ran unrecorded). The window then opens only after the frames since the warm-up have settled (`settleFrames`, the A/B switches' rule): `switches` has a `window`/`start` row, and `fetch --ab` flags a window the page never settled for.

**Lengths** (`BENCH`, named constants; all in `bench-measure.ts`). The window 30 s to **40 s** (`measureS`) and each A/B block 3 s to **8 s** (`blockS`): a few seconds more per setting, the stability check below says whether it was enough. Cuts, to hold a step near 5 minutes on a quiet desktop: the pacer A/B 3 rounds to **2** (`paceCycles`: the 1/80 s arm's third round and the 1/240 s arm's with it), the detail A/B's **75 m rung** (`DETAIL_ARMS`: the arm between no cuts and 50 m), the sky A/B's **second round** (`skyCycles` 2 to 1). The FX A/B stays at 2 rounds. A step on a quiet desktop: sweep about 39 s with Ultra (first of a page) or 6 s, warm-up 20 s of race clock, settle, the window 40 s, A/Bs 32 + 48 + 48 (64 with Ultra) + 16 s, the replay, and about 20 settle watches of 1 s or more each; on llvmpipe at 10 fps the settle cap (6 s) is the long part.

**Stability check.** `result.simSpreadPct` (the window) and each arm's `simSpreadPct` (a `Block`) are the coefficient of variation, in %, of the sim's ms per sim-second over the seconds the window or the arm's blocks covered whole (an arm's block bins its frames by wall second, counting a second the block spent at least half in; arrays sized once): the number says whether the mean means anything. The card prints it (`±N %` after an arm's ms/sim-s, and `N % spread over its seconds` in the phase line); an arm whose switches never settled says so (`Block.unsettled`: `N switches never settled!`). `fetch --ab` flags a window over 25 % spread (`UNSTEADY_SPREAD_PCT`).

**Per-second series** (`result.phases.perSecond`). For each wall second the window crossed: its wall span, the sim seconds it covered, each phase's ms and each work counter's count per sim second, an array a name (`watchWork().tick`, called once a frame: one comparison until a second is crossed, then a copy of 10 phase and 22 counter cells into arrays sized once). They are in the JSON and in `node scripts/fetch-submissions.mjs <url> --kind bench --series` (a row a second), **not** on the card. A window's 50 entries with 7-digit counts are 12.5 kB of the 48 kB cap after rounding (`roundCard`; measured), and a row in `engine-bench-report.test.ts` keeps the whole card with every series full 12 kB under the cap.

**Cost per unit of work by class** (`result.phases.unitUs`, `UNIT_COSTS`): us per live car-slice for drive and integrate, per car-slice of any class for integrate, per wreck car-slice for the wreck and structure phases, per pair test for the pairs phase, per prism query for the course phase; a unit the window never stepped has no entry. Printed by `--phases` and as extra rows of `--ab` (the arms do different work, so these are the numbers to compare).

**Page state** (`result.pageState`): `stepOfPage` (steps this page ran before: 0 is the page's coldest), `keep` (the loop's keep flag), `heapUsedMB` / `heapLimitMB` at the window's start (Chrome's `performance.memory`, else null) and `ragdollHost` (`remote`: the page's ragdoll worker was in use, `inline`, or `none` yet). The loop is now one page, so the old question "is the previous page's worker still alive" is the page's own worker; `fetch --phases` prints the line.

**Observer effect of these recorders** (node, the real engine's parts; throwaway measurement run once, not a test row). `watchWork().tick` in a frame inside the current second: 1.7 ns; at a second boundary (once a second): 0.15 us; the arm's per-frame bins: 3.3 ns; 5 million calls of each trigger no garbage collection (the `gc` performance observer: zero events). Against a 4-100 ms frame that is under 0.0001 %. The sim is bit for bit unchanged by recording: `bench-scene.test.ts` runs city, city with the activation, the strip and the city again with `watchWork` ticking every frame, and the second city's digest (every car's pose and velocity, the pacer's steps) equals the first city's, which ran with nothing recording.

### Where the sim's time goes: phases, work counters, device state

The card's `simMsPerSimS` is one number; `result.phases` says where it went, so a card from a phone can be read against a desktop's phase by phase. It is measured over the 30 s window only (the clock reads are switched on at its start and off at its end: `World.phases.on`, `watchWork` in `bench-measure.ts`; the A/B blocks and every other run read no clock). `phases.msPerSimS` is main-thread sim ms per sim-second in each phase of a step, `phases.unattributedMsPerSimS` is `simMsPerSimS` less their sum (the pacer's own loop and the pose blend between steps, a few ms), so the table sums to the headline. The phases tile `SimPacer.run`'s step (`CrashEngine.slice`), each boundary one `performance.now()` read (`sim-phases.ts` `lap`):

| Phase | From … to … | What runs in it |
|---|---|---|
| `drive` | the slice's start to `stepWorld` (`engine.ts` `slice`, `fixedStep`) | pose blend begin, every car's input: the race AI, police and traffic `think`s, the seat, netplay's drive, a wreck's coast, rig sync |
| `plan` | `stepWorld`'s start to its first slice (`world-step.ts`) | roof surfaces, near pairs (`collectNear`, `markApproaches`, `carsInReach`), the slice count, the cars' surface sync |
| `integrate` | per car, per slice: `beginSlice` to its pose refresh | a car on its drive's law: `integrate`, `syncPose` / `refreshBasis` (also the slice a rig steps itself). A step cut to fine slices runs a lone car (`loneCars`, [`CONTACT_PARITY.md`](CONTACT_PARITY.md) "Lone cars") once, at the step's length, in its first slice: one lap for it where a car in contact has `slices` |
| `wreck` | the same window, for a car whose rigid body steps (`deform.massActive`) | `integrateWreck`: the rigid step of crashed cars |
| `pairs` | after the integrates to `armCrushRows` | roof sync, part contact (`partContactPair`), the barrier, every near pair through `resolveCarPair`, the wrecks' pose sync |
| `structure` | the structure loop | `stepStructure` (the crush solve), `syncPose`, the barrier's clip, `afterContacts`, `afterCar` |
| `course` | the `collide` hook | `RaceDirector.collide` → `courseHit`: the road projection and the prism contacts (`propContact`) of walls and props |
| `bake` | `endSlice`, `bakeBetweenSlices` | the slice's bake of each car's body |
| `rules` | `stepWorld`'s end (`ejection.step`) to the end of `fixedStep` | ejections and the thrown drivers' launch, `RaceDirector.step` (police, recorder, race rules), the crash cinematic's start |
| `settle` | `settleStep` | the dead drivetrain's drive, the wreck's slide, `stepBreakage` (hinges, tears, lamps, glass) |

Skinning (`updateSkin`, the WASM kernel) and the ragdoll hand-off run in the frame outside `SimPacer.run`, so they are not in `simMsPerSimS`; their work is in the counters below.

`phases.workPerSimS` counts the work per sim-second, which no timer noise touches, so a rise in the amount of work reads apart from a rise in its cost per unit. The counters are plain adds, kept always; the window reads the differences. `steps` the pacer's steps, `slices` the slices they were cut to; `liveCarSlices`, `wreckCarSlices`, `asleepCarSlices` car-slices stepped for a car on its drive's law, a wreck whose rigid body runs, and a sleeping wreck; `pairTests` near pairs that went through `resolveCarPair`, `pairContacts` those that hit, `partContacts` door, mirror or panel contacts; `prismQueries`, `prismsVisited`, `prismTouches` a car's footprint queries of the course's prisms (`Surface.prismsNear` by `propContact`), the prisms they returned, and the ones the footprint touched; `skins`, `skinVerts` cars skinned by the WASM kernel and their vertices (0 where the kernel did not load); `ragdollMessages`, `ragdollBytes` what the sim posted to the ragdoll worker (messages, and the bytes of the typed arrays handed over: a frame's cars, a car's cage; 0 until a driver is thrown or a prop knocked). The fine-slice cuts per sim-second (`fineCutsPerSimS`) and the ragdoll world's steps (`ragdoll.steps`) are the card's existing counters.

**Epicenter activation (`epi.on`).** `nodesLoose` and `nodesLocked` count the soft-body nodes of the crashed cars a structure step ran the solver on and the ones it left riding the body (per car-slice, every crashed car: today every one outside the 0.35 s contact window is locked); `frozenCarSlices` the car-slices of wrecks frozen by the relock (`DeformRig.frozen`: no solve, no frame re-measure, a cached rigid step), `freezes` and `thaws` how often a wreck froze and thawed (a contact thaws it). With the activation on the race is not bit-identical to `whole` (a frozen wreck skips the seat step and the clamp: a few millimetres, and a closed-loop race then diverges through its contacts), so the arms do different work: **quote cost per unit of work** (ms per wreck car-slice by class, per intact car-slice, structure ms per wreck slice), never phase totals, and print the counters beside them. The bench loop runs every map off and on (`&epi=1`, above), the pair's order alternating with the cycle (off then on, then on then off: the second page of a pair loads onto a warm device and a collected heap); outside the bench page the A/B is `#epi.on=1` against none (the Debug panel's Epicenter group, `epi.*` keys, `docs/ARCHITECTURE.md`). `epi.presentSkip` and `epi.nearPrune` are the exact cost cuts and are on in both arms (independent of `on`; digests equal to 0 on the city race, the derby and a pile, `cage-draw-independence.test.ts` for the drawn crash): an arm of the headless tool turns one off with `epi.presentSkip=0`.

**Exact cuts proved slice by slice (`--slices`, `--verify`).** `epi.wreckTops` (a wreck's hull points leave out the tops of other wrecks, whose rows its step drops anyway) and `epi.preClear` (a cage point whose height from the body's axes stands over the static bound by the most it can fall in the slice is clear without its arm, velocity or box) are exact cost cuts, on by default like `presentSkip` and `nearPrune` and independent of `on` (clean-load, same work, bit-identical digests: the whole sim -9.3 % city, -13.3 % mall, -19.8 % dam spine per car-slice with `wreckTops`; `preClear` is free alone and a further 3-7 % off the wreck step beside it; the worker's load was 1.5-2.6, one foreign busy core of 16). `bench.mjs run <row> --arm base: --arm x:epi.wreckTops=0 --slices` logs every car-slice of both arms (contacts, `frozen`, velocity, spin, pose) and prints `slice-by-slice, A vs B: N / N car-slices logged; IDENTICAL` or names the first physical difference (`slice-log.ts`); `hardTouch` alone may differ (a derived bit nothing of a wreck reads: `contactHz` answers 0 for a `massActive` car before reading it) and is counted apart. A keyframe carries `hardTouch`, so a clip recorded with a knob at 0 replays under 1 with the same poses, velocities and crush at every step (its recorded bit differing at most); a clip recorded before a knob existed reads it at its default (`DEFAULTS` in `epicenter.ts`: 1 for both, exact, so it replays the same). `--verify` adds the counters that must be 0: `wreckTops check` (a skipped point whose old query would have made a contact row or set `nearing`), `preClear check` (a point the own test would not have cleared; the least margin printed is `CLEAR_ROUND`, 1 um) and `whole-body gate check`. A relock, a thaw and `epi.on` itself are not exact (above): never prove them this way.

**The put-away cars (`epi.storedSkip`).** Every race with traffic or police keeps 8-16 cars the director has put away (`EngineRaceField.putAway`: reset, hidden, still at (4000 + 12 slot, 4000), 4 km from any course; `DeformableCar.stored`, set each step from `dormant`): they were stepped like any car, 3 % (city) to 17 % (mall) of the sim, and on the Mall each cost 77 us a slice because off the baked grid the terrain bound sums every hill. With the knob on (default) `stepWorld` leaves them out of every per-car loop and only drops the weight carried on their roof (`takeBorne`, which a step would take and zero: left in the slot it reached the car's first step after the director placed it again, and broke a 45-contact pile of the strip bit for bit 27 s in). Proof: `bench.mjs run <row> --arm main:epi.storedSkip=0 --arm skip: --slices` leaves the slice logger out of put-away cars (`slice-log.ts`) and compares every other car-slice: city-race 182 768, mall 113 966, dam spine 115 877, strip 123 330 records over 40 s, all IDENTICAL, and the new `digest of the cars not put away` row (the digest over the cars not put away at the end: `digestLive` in the arm's JSON) equal. Whole-sim wall (--force, load 1.1-1.9): city -3.3 %, mall -17.3 %, dam spine -9.8 %, strip -9.3 %.

**The clock.** Firefox rounds `performance.now()` to 1 ms (`timerStepMs`). Each phase is a sum of differences of that clock over thousands of laps, and a lap's start is uncorrelated with the tick, so the rounding errors cancel: the sums are unbiased, a per-lap maximum would not be, so the card keeps sums only. A clock of 16.7 ms (resistFingerprinting) blinds the pacer (`SimPacer`) as well and the phases there are noise.

**Cost.** One clock read per boundary, about 10 000 a sim-second in the city bench (a lap per car-slice in `integrate` / `wreck`, a few per step); off it is one branch each. Measured in node on the bench race (`BENCH_RACE`, seed 1, 15 AI and police, the pacer pinned to 1/240 s, 20 s of sim after 10 s of warm-up, six interleaved process pairs of the same sim): 10 507 ms mean with the clock off, 10 494 ms on (-0.1 %, pairs from -1.8 % to +2.0 %, the machine's own noise); `performance.now()` costs 30 ns there, 10 000 reads a sim-second is 0.3 ms of the 520. The sim is bit-identical either way (the digest of every car's pose and velocity and the pacer's steps, the same with the clock on and off: `engine-bench-headless.test-util.ts` `simDigest`; the window's `simMsPerSimS` includes the reads). A browser's clock reads may cost more than node's; a card whose `phases.unattributedMsPerSimS` is a large share of `simMsPerSimS` is where to look.

**Device state.** `device.battery` (`start` and `end`: `charging`, `level` 0-1; null where `navigator.getBattery` is missing: Chrome has it, Firefox and Safari do not), `longTasks` (`count`, `totalMs`, `maxMs` of the main-thread tasks of 50 ms or more over the window, `PerformanceObserver` "longtask"; null outside Chrome). Already on the card: the page's visibility and focus changes (`pageEvents`), `device.dpr` and `device.canvas` (the canvas actually rendered), `settings.deviceRatio`, `settings.pixelRatio`, the FX tier share (`tierPct`).

**Reading the cards.** `node scripts/fetch-submissions.mjs <app url> --kind bench --phases` prints each bench card's phase table (phases, work counts, long tasks, battery) under its line, for the cards already saved too; a card from before the phase table says so. The submissions endpoint stores a bench card's result as sent (`payload` is any JSON object under the 48 kB cap; the new fields add under 1.5 kB), so nothing server-side filters them.

`--ab` pairs the loop's off and epicenter cards by session, cycle and map (`submission.settings`; the arm is the card's `settings.epicenter`, else the step's `:epi` suffix) and prints one block per pair: ms per sim-second by phase, the counters, the cost per unit of work (µs per live car-slice for integrate, per wreck car-slice for wreck and structure; the frozen share of wreck and asleep car-slices), the hitched frames, and a `FLAG` line for an arm whose window was spoiled and for a pair whose arms ran different FX tiers: such a pair says little about the activation. **What is a FLAG and what a note** (`windowReading`, `focusCost`): a FLAG for seconds the page was **hidden**, the **screen wake lock not held**, the **sky not as pinned**, **not fullscreen on a phone or tablet** (the user agent says so), **frame rate throttled** (a window second of 2 frames or fewer: a browser holds a page it does not draw; a steady 10 fps is not that) and **focus loss that cost frame time** (below). A note, not a FLAG, for seconds **visible but unfocused** (a desktop with two monitors is unfocused whenever its owner types or works on the other one, and a visible page draws at full rate) and, on a desktop, seconds out of fullscreen. The focus check compares the mean frame time (1000 / `fpsPerSecond`) of the window's unfocused-visible seconds with its focused ones (the focus state of each second from the window's `pageEvents`, which count from the window's start like `fpsPerSecond`; at least 2 seconds of each) and FLAGs only when they differ by more than the window's own frame-time spread (the coefficient of variation of its seconds) and at least 5 % (`MIN_FOCUS_DIFF_PCT`: a steady window must not flag a rounding difference); the note gives both frame times and says `no cost` otherwise. A card from before the series falls back to its `pageEvents` for hidden / unfocused / fullscreen, without counts.

### Hitches and settling: what a switch costs, kept out of the arms

**Settle rule** (`bench-settle.ts`, `SETTLE`). An A/B arm is scored only after its switch has settled, not after a fixed number of frames. After each switch the frame intervals are watched until the newest 30 are steady: no frame of them more than 3 x their median (a hang is a spike), and their median within 20 % of the 30 before. Those frames are unscored. An arm that is not steady after 6 s **and** 120 frames (the frames matter on a phone at 10 fps, where 6 s is 60 frames) is scored anyway and the card marks it `!`. Each switch's longest frame (ms) and time to settle (s) are the card's `switches` and its `switch hitches` text; they are never in an arm's fps, frame, cpu or sim numbers. The old rule took 10 frames: a hang that falls over 30 frames put its tail into the arm.

**Hitch log** (`bench-hitch.ts`, `result.hitches`). Every frame of the whole run (warm-up, window, each A/B, replay) over 3 x the running median interval (128 frames) and at least 25 ms is a hitch. The table keeps the worst 48 (a full table with 30 switches is 12 kB under the submission cap with room for the HUD: a row in `engine-bench-report.test.ts`) (their count and the ms they ran over the median stay whole): the stretch of the run (`PAGE_PHASES`), seconds into it, the interval, the engine's ms in it of which sim and draw, and what changed in that frame (`CAUSE`): `setting-switch` (an A/B arm's settle was being watched), `focus` (the page's focus or visibility changed within 1.5 s), `crash` (a car became a wreck), `ragdoll-post` (3 or more messages posted to the worker in a frame: a throw or a cage), `shader` (a program was added), `gpu-resources` (textures or geometries were created or freed), `cold` (the first 2 sim seconds of the page). A hitch with no cause is one the bench cannot see: GC, the OS, another process (GC is not detectable without allocating per frame: `performance.memory` makes an object each read). The card's `hitches:` line names the worst four.

**Observer effect.** Both are flat typed arrays sized once; nothing allocates in a frame (the numbers travel in the frame's `Float64Array` row, since a double passed to a call that is not inlined is boxed). Measured in node: `HitchLog.frame` 174 ns a frame, `SettleWatch.push` 15 ns (only while settling): 0.004 % of a 4.2 ms frame. A million `HitchLog.frame` calls with 100 hitches stored and dropped trigger no garbage collection (`bench-hitch.test.ts`, the `gc` performance observer). The per-frame cause read (`readCauses`) is ten property reads and a loop over the cars.

**What a tier switch cost, and the fix** (headless Chromium on a software GL, llvmpipe, 32 cars, the city race; not a phone, so read the ratios, not the ms). A switch to Low or High took the first frame 330-1000 ms to draw (`draw` inside the engine's tick; the other frames of the switch were ordinary). Isolated by switching with and without the rival redraw: the switch to High redraws and re-uploads every rival bitmap (`RivalLooks.useTier`: 57-93 ms of dressing 32 cars, and the first draw uploads 20.6 MiB with mips: 140-340 ms more) and a step back down freed them again, so every rise paid it. Two changes: `RivalLooks.useTier` never shrinks the drawn size (a step down keeps the finer bitmaps: the redraw and the upload happen once, on the first rise to a size; memory stays at the finest size visited, 20.6 MiB at High and 82.7 MiB at Ultra on a desktop, until the page closes), and `PostFX.prime` draws every pass of the post chain once at boot under the zero scissor (the bloom targets' storage and the passes' first-draw link check: about 3 MB of GPU memory at 1280 x 800, allocated at boot instead of on the first pick). Measured before and after in the same browser: the first frame after minimal to Low 709 ms to 121 ms (the steady frame is 98 ms); the draw of a rise to High already drawn once 477-848 ms to 241-380 ms; the first rise to High 935 ms to 599-702 ms. **Not fixed:** each rise to High still has one frame of 240-480 ms to draw against 120-150 ms steady, with no redraw, no program added and nothing the bench's counters name; the cause is not isolated.
